## 可以做什么

- 免费使用、学习、修改和自行部署 Twilight。
- 对 Twilight 进行二次开发并发布自己的改版。
- 销售软件副本、收费部署、提供商业托管、订阅服务、技术支持或定制开发。
- 增加改版名称、改版作者、公司名称、商标和改版仓库地址。

许可证不禁止商业行为。收费与是否必须开源是两个不同问题：可以收费，但不能把受许可证约束的改版闭源。

## 必须履行的义务

### 分发软件或改版

向他人提供源代码、二进制、容器镜像、安装包或其他软件副本时，必须：

1. 继续按 GNU AGPL v3 或更高版本许可整个受覆盖作品。
2. 同时提供或按 GNU AGPL 允许的方式提供完整对应源代码。
3. 保留根目录 `LICENSE` 和 `NOTICE`，并在随附材料中提供许可证与源码获取方式。
4. 明确标记自己做过的修改，不得把改版冒充为上游官方版本。

### 通过网络提供服务

如果修改后的 Twilight 通过网站、面板、API 或其他网络方式与用户交互，即使没有向用户交付二进制文件，也必须依据 GNU AGPL 第 13 条，让这些网络用户能够获得服务器实际运行版本的完整对应源代码。

源码必须对应正在运行的版本，包含构建、安装和运行该版本所需的受覆盖源码与脚本；只提供旧版仓库地址、残缺源码或无法对应线上版本的代码不满足要求。

### 保留原始署名和上游地址

所有原版和改版必须保留以下法律声明：

- 原始项目名：`Twilight`
- 原始版权署名：`Copyright (C) 2025-2026 Prejudice Studio`
- 上游开源地址：`https://github.com/Prejudice-Studio/Twilight`
- 许可证：`GNU AGPL version 3 or later`

可以在旁边增加改版信息，但不得删除、隐藏、替换、弱化或错误表述这些原始信息。带交互界面的改版必须保留一个容易访问的“法律信息”“关于”或“源代码”入口，展示上述信息、实际运行版本的源码地址和许可证。

Twilight 当前在登录后的桌面侧栏、移动菜单和部分管理界面提供上游项目入口。改版可以调整位置和样式，但必须提供同等清晰、容易访问的替代入口，不能直接删除。

## 不允许的做法

- 删除 `LICENSE`、`NOTICE`、原始版权署名或上游开源地址。
- 将修改版改成闭源、仅提供二进制或只公布与线上版本不对应的源码。
- 通过 SaaS、托管面板或其他网络服务规避源码提供义务。
- 用自己的项目名或公司名替换 Twilight 与 Prejudice Studio 的原始归属，使用户误以为改版是完全独立创作或官方版本。
- 施加会阻止接收者继续行使 GNU AGPL 权利的额外限制。

Twilight 在 2026 年 8 月 25 日此次换证提交之前曾按 MIT License 公开发布。已经授予的开源许可证不能被追溯撤销，因此此前公开版本仍可按当时的 MIT 条款使用。

根目录的 `LICENSES/MIT-legacy.txt` 仅用于保存历史授权和履行旧代码的署名义务，不代表当前版本同时提供 MIT 与 GNU AGPL 双许可证。当前提交及之后的版本应按 `LICENSE` 与 `NOTICE` 执行。

## 常见场景

| 场景 | 是否允许 | 主要要求 |
| ---- | ---- | ---- |
| 自己部署未修改版本 | 允许 | 保留许可证和署名；向用户展示现有源码/法律入口 |
| 修改后仅在自己服务器提供服务 | 允许 | 向网络用户提供实际运行版本的完整对应源码 |
| 出售安装服务或技术支持 | 允许 | 不得闭源；保留署名、许可证和源码地址 |
| 发布自己的商业改版 | 允许 | 改版整体继续使用 GNU AGPL，并提供完整对应源码 |
| 只发布 Docker 镜像或二进制 | 不允许单独这样做 | 还必须按 GNU AGPL 提供完整对应源码与许可证材料 |
| 删除 Twilight、Prejudice Studio 或上游地址 | 不允许 | `NOTICE` 的 GNU AGPL 第 7(b) 条署名要求必须保留 |
