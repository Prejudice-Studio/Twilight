## 三、根本原因分析

### 3.1 V2 设计范围有限

V2 API 设计时主要聚焦于：
- ✅ 核心用户管理（users）
- ✅ 基础认证流程（auth）
- ✅ Emby 集成（emby）
- ✅ 工单系统（tickets）
- ✅ 公告通知（announcements）

**未覆盖的领域**：
- ❌ 第三方集成（APIKey、Bangumi）
- ❌ 管理工具（批量操作、邀请树）
- ❌ 装饰功能（签到积分）

### 3.2 前端迁移不彻底

1. **开关声明与实现脱节**：`useV2.bangumi`、`useV2.invite` 等有声明但方法实现未加条件分支
2. **缺少模块开关**：批量操作、签到、APIKey 等模块没有对应的 `useV2.*` 开关
3. **硬编码 V1 路径**：部分端点直接写死 `/api/v1/` 前缀，未通过条件判断

### 3.3 文档与代码脱节

`docs/v2-compatibility-verification.md` 声称：
> V2 后端已实现完整的 API 路由

但实际覆盖率仅 **52.6%**，文档过于乐观。

## 四、立即行动建议

### 4.1 紧急风险缓解（1 天内）

**问题**：当前 `NEXT_PUBLIC_USE_V1_COMPAT` 默认为 `false`，即默认启用 V2 API。  
**影响**：用户访问缺失的 V2 端点时会遇到大量 **404 错误**。

**建议**：
```typescript
// webui/src/lib/api.ts
private useV2 = {
  // 反转默认值：V1 为默认，V2 需要显式启用
  auth: process.env.NEXT_PUBLIC_USE_V1_COMPAT === 'false',  // 改为 === 'false'
  users: process.env.NEXT_PUBLIC_USE_V1_COMPAT === 'false',
  // ...其他模块同理
};
```

或者环境变量层面：
```bash
# .env.local
NEXT_PUBLIC_USE_V1_COMPAT=true  # 强制使用 V1 作为默认
```

## 六、风险与约束

### 6.1 技术约束（严禁违反）

1. **CORS/CSRF 策略锁定** ⚠️  
   - 严禁修改 CORS/CSRF 实现（历史事故 commit 12225e4c）
   - 新增 V2 端点必须遵守现有策略

2. **数据库兼容性**  
   - V2 端点必须能操作 V1 创建的数据
   - 禁止引入 schema 迁移

3. **会话管理**  
   - V2 必须复用 V1 的会话 cookie
   - 公开端点必须使用 `credentials: "omit"`

### 6.2 业务风险

1. **用户体验降级**  
   - 当前默认启用 V2，缺失功能会直接报错
   - **建议短期内反转默认值**：`useV2.* = false`（V1 为默认）

2. **生产环境回退**  
   - 保留 V1 API 作为紧急回退路径
   - V2 稳定前不要删除 V1 代码
