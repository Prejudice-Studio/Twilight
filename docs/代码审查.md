### 审查范围

- 范围：Telegram Bot HTTP/JSON 协议层、`getUpdates` 长轮询响应解码、固定请求 DTO、错误与超时边界
- 目标：减少监听热路径 CPU 与临时内存，同时保持指令字段、429 退避、SSRF/重定向和脱敏语义

### 已修复问题

- 旧成功路径会先 `io.ReadAll` 整包，再把 `result` 保存成 `json.RawMessage`，最后二次 `json.Unmarshal`；每批更新产生额外整包复制和解析扫描。现改为泛型 envelope 直接解码目标结果，写操作以零保留类型跳过无用结果对象。
- `sendMessage`、`editMessageText`、`deleteMessage`、callback、成员查询/封禁及 `getUpdates` 改用固定请求结构；兼容测试锁定可选字段、省略 offset 和显式 `false` 字段，避免优化改变 Telegram 请求语义。
- 成功响应限制为 4 MiB，拒绝尾随第二个 JSON 值；错误正文最多读取 1 MiB。3xx 优先报告被拒绝重定向，不再让 HTML 正文掩盖 Location；网络错误、错误正文和 Location 中的 Bot Token 均经 App 层脱敏。
- 调用方已有 context deadline 时不叠加或替换为 20/45 秒默认值；真实 HTTP 429 继续解析 `parameters.retry_after`，批处理退避行为不变。

### 验证与结论

- 100 条更新基准：旧路径 `696330-742701 ns/op`、约 `453304 B/op`、`3529 allocs/op`；新路径 `418333-450198 ns/op`、`322065 B/op`、`3520 allocs/op`，耗时下降约 35%-40%，临时内存下降约 29%。
- PostgreSQL 真库：`internal/api` 全量测试通过（约 149 秒），`internal/store` 全量测试通过；其余 Go 包测试、`go vet ./...`、`go build ./...` 均通过。
- 结论：`Approved`。未发现 CORS 行为改动；Windows 环境缺少可用 C/C++ 编译器，本轮没有 race detector 动态证据。
- 后续方向：更新对象仍使用动态 `map[string]any`，其字段级分配是当前主要剩余成本；若后续改为强类型 update DTO，必须先完整覆盖 message、callback、chat member 与 inline 顺序语义。
